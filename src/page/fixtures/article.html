Choosing an allocator for a Rust CLI

By Ada Example, 2 November 2026

Command-line tools start, do one job and exit. That shape changes which memory allocator wins, because a tool that lives for two hundred milliseconds never reaches the steady state that server benchmarks measure. This post walks through the numbers we gathered while profiling a search client that fans out to a dozen providers at once.

Why the default allocator

The system allocator is the safe default. It is what every crate is tested against, it costs nothing in binary size, and on macOS it is surprisingly fast for small allocations. On Linux with glibc the story changes once many threads allocate concurrently, which is exactly what an async runtime with a worker per core does when a dozen responses arrive together.

We measured a 14 percent reduction in wall time for a fan-out of twelve requests by switching to mimalloc, with most of the gain coming from JSON parsing of the larger responses.

What we shipped

We kept mimalloc behind a single global allocator declaration in main, measured the binary size cost at about 120 KB stripped, and documented how to turn it off. The change took ten minutes and has needed no attention since, which is the best thing one can say about an allocator.

  • Measure on the platform you ship to.
  • Measure the whole command, not a micro benchmark.
